# 🦀 RustChat — 500인 멀티채팅 서버

> 국민대학교 시스템최신기술 26-1 Part 2 / C조 도전과제 프로젝트

## 프로젝트 소개

Rust의 비동기 런타임 `tokio`를 기반으로 구현한 **500인 동시접속 멀티채팅 서버**입니다.  
단순한 메시지 전달을 넘어, **실시간 투표 시스템**과 **적대적 봇 테스트**를 통해  
어떤 상황에서도 Race Condition 없이 안전하게 동작함을 증명합니다.

## 기술 스택

- **Language**: Rust
- **Async Runtime**: tokio
- **동시성**: `tokio::sync::broadcast`, `Arc<RwLock<HashMap>>`
- **프로토콜**: TCP 소켓

## 주요 기능

- 최대 500명 이상 동시접속 단톡방
- 실시간 브로드캐스트 메시지 전송 (Lock-Free 구조)
- **실시간 투표 시스템** — 500명 동시 Write-Heavy 환경에서 Atomic 연산 기반 집계
- 4가지 악성 봇 시나리오를 통한 적대적 테스트
- 메시지 수신 누락 여부 검증 (누락률 0% 목표)

## Race Condition 해결

### 1.1. 문제 정의

- **현상:** 500명의 유저가 동시에 접속하여 통신하는 환경에서, 참여자 목록(상태) 관리와 메시지 브로드캐스팅 로직이 결합되어 있을 경우 심각한 Lock 경합(Contention) 발생
- **영향:** 잦은 Lock 점유로 인해 브로드캐스트 전송 지연 및 서버 전체의 성능 병목 현상을 초래할 위험 존재
  - 특히 500명에게 순차 전송하는 동안 Lock이 계속 잡혀있으면, 그 사이 입장/퇴장이 블로킹되는 문제 발생

### 1.2. 해결 방안

**핵심 전략: 상태 관리(참여자 목록)와 메시지 전달(브로드캐스트)의 완전 분리(Decoupling)를 통한 Lock 의존성 제거**

- **메시지 브로드캐스트 (Lock-Free 구조 전환)**
  - 채팅방 전체를 아우르는 단일 `tokio::sync::broadcast` 채널 도입
  - 클라이언트는 입장 시 `.subscribe()`를 호출하여 개별 수신기를 발급받음
  - 메시지 발송 시 유저 목록 Lock 없이 전역 채널에 `tx.send()` 1회 호출만으로 500명 전원에게 즉시 브로드캐스트

- **참여자 목록 관리 (Lock 범위 최소화)**
  - 유저 메타데이터(ID 등) 관리에 한하여 `Arc<RwLock<HashMap>>`을 제한적으로 적용
  - 입장/퇴장 시에만 Write Lock을 짧게 점유하도록 설계

```rust
// 브로드캐스트: 전역 채널로 Lock 없이 전송
let (tx, _rx) = broadcast::channel(1024);
tx.send(msg)?; // Lock 없이 500명 전원에게 전송

// 참여자 목록: 입장/퇴장 시에만 write lock 점유
clients.write().await.insert(id, metadata); // write lock 즉시 해제
```

## 차별화 전략 — 실시간 투표 시스템

같은 채팅 서버를 구현하는 팀과의 차별점으로, **500명 동시 Write-Heavy 환경**을 설정합니다.

- **기술적 도전**: 500명이 짧은 시간 내 동시에 투표(쓰기 요청)를 보내는 상황
- **해결 방안**: `Mutex` 대신 **Atomic 연산**과 Lock-free 알고리즘으로 병목 없는 초고속 집계 구현

## 테스트 전략

### 1. 순수 채팅 테스트 (기본 동작 검증)

일반 봇 500명이 각자 다른 메시지를 전송하고, **전원이 모든 메시지를 수신했는지** 검증합니다.

| 봇 유형 | 역할 | 검증 목표 |
|--------|------|---------|
| 🙂 **일반 봇 500명** | 각자 고유 메시지 전송 | 누락 없이 전원 수신했는지 |

```bash
# 일반 봇 500명 실행
cargo run --bin bot_normal -- --count 500

# 검증: 봇 ID + 시퀀스 번호로 누락 여부 확인
# 전송: 500명 × N개 메시지
# 수신: 500명 × N개 메시지 ✅
```

### 2. 대규모 인터랙션 테스트 (투표 정합성)

일반 봇 + 변덕쟁이 봇을 섞어 **투표 결과가 정확히 집계되는지** 검증합니다.

| 봇 유형 | 역할 | 검증 목표 |
|--------|------|---------|
| 🙂 **일반 봇** | 정상적으로 투표 전송 | 누락 없이 집계되는지 |
| 🔀 **변덕쟁이 봇** (Rapid Toggle) | 0.01초 단위로 투표 변경 | 최종 값이 정확히 반영되는지 |

```bash
# 일반 봇 450명 + 변덕쟁이 봇 50명 동시 실행
cargo run --bin bot_normal -- --count 450
cargo run --bin bot_toggle -- --count 50

# 검증: 서버 집계 결과 vs 봇이 보낸 최종 투표 수 비교
# 서버: 찬성 247, 반대 253 (총 500) ✅
```

### 3. 악성 봇 테스트 (서버 내구성)

"서버가 돌아간다"를 넘어 **"어떤 상황에서도 터지지 않는다"** 를 증명합니다.  
악성 봇은 정상 테스트와 별도로 실행합니다.

| 봇 유형 | 설명 | 검증 목표 |
|--------|------|---------|
| 📨 **도배 봇** (Spammer) | 초당 수백 개의 패킷 전송 | 서버 크래시 없는지 |
| 👻 **잠수 봇** (Ghost Client) | 연결만 유지, 데이터 미수신 | 메모리 누수 없는지 |
| 💨 **탈주 봇** (Abnormal Quitter) | 투표 직후 강제 종료 | 서버 패닉 없는지 |

```bash
# 각 악성봇 타입별로 독립 실행
cargo run --bin bot_spammer -- --count 50
cargo run --bin bot_ghost -- --count 50
cargo run --bin bot_quitter -- --count 50
```
